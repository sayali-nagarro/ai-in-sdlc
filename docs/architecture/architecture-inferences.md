# Architecture diagram assumptions and inferences

These are interpretations used to make the diagrams readable. They are not additional implementation facts. See the [citation register](./architecture-citations.md) for supporting source locations.

| ID | Assumption or inference | Why it was necessary | Evidence missing | How to verify | Effect on architecture correctness |
|---|---|---|---|---|---|
| A01 | The as-built process box represents the ASP.NET Core application configured by `Program.cs`, not one guaranteed production instance. | A container diagram needs a runtime boundary. | Hosting manifests, deployment topology, replica count and scale-out configuration are absent from application source. | Inspect approved deployment/IaC and runtime environment; do not infer from `ops/` incident samples. | Medium: the code boundary is correct, but it says nothing about deployed instance topology. |
| A02 | The browser and the server-hosted static files are drawn as separate elements; JavaScript runs in the browser. | This distinguishes the UI client from the API host despite static assets being served by the same app. | No separate frontend deployment or browser deployment topology is specified. | Confirm deployment and inspect the app in a supported browser; source shows the static-file middleware and client-side `fetch`. | Low for code architecture; medium if a separate frontend host is later introduced. |
| A03 | The as-built sequence shows a successful submit followed by a decision in one illustrative browser session; it does not assert that policy requires the same person to submit and approve. | A complete state path is Draft → PendingApproval → Approved/Rejected, while no separate submitter role is enforced. | Business policy about submitter/approver separation and whether they must be different users is absent. | Obtain the approved role/separation-of-duties requirements and add a test if separation is required. | Medium: would affect authorization and workflow controls, not the current method-call sequence. |
| A04 | The as-built sequence begins with a valid signed-in session and shows the UI's submit and decision interactions, rather than replaying the login UI flow. | The task centers on approval, and `/api` actions require a bearer session. | No specific assignment requirement says the login transaction must be part of the sequence. | Compare with the requested sequence scope; sign-in behavior is independently cited in the container diagram. | Low: it omits a precondition-establishment step but not any approval call. |
| A05 | The target's SQL-backed repository is represented as an implementation of the existing interface, but no concrete type name is chosen. | The target-state document proposes SQL persistence and the existing interface is its natural seam; the existing target diagram itself labels `SqlInvoiceRepository` as an agent-proposed name. | Approved class structure, repository method semantics, schema and migration design are absent. | Confirm an approved ADR/design and schema before implementation. | Medium: the dependency direction is supported, but implementation internals remain undecided. |
| A06 | The target diagram uses generic invoice, audit and outbox data labels rather than asserting table names or full schema. | The draft ADR specifies the data written and transaction boundary but does not define the table/schema names. | Schema definitions, retention implementation and migration plan are absent. | Review approved database design and migrations when produced. | Medium: logical data responsibilities are represented; physical schema is intentionally unresolved. |
| A07 | The worker and Unknown resolver are shown as logical behaviors, not as separate deployable services or a specified hosting location. | The ADR requires a worker and a resolver but does not settle their process boundary; it only estimates the worker could run on the existing App Service plan. | Approved hosting/deployment topology and ownership are absent. | Confirm deployment design and operational ownership. | Medium: runtime topology is unknown; no incorrect host is asserted in the diagram. |
| A08 | The target approval transaction is shown as a design requirement, not a current guarantee. | The draft ADR explicitly requires invoice approval, audit row and outbox row to commit together. | The ADR is marked draft and has not established a built implementation or owner sign-off. | Obtain ADR approval and verify the eventual transaction with integration tests. | High if mistaken for implemented behavior; the diagram labels it planned and the register cites the draft. |
| A09 | PayEx submission, duplicate prevention, lookup and reconciliation are requirements with unresolved vendor contract details. | The draft ADR makes an exactly-once payment effect conditional on atomic PayEx deduplication (or an equivalent unique-reference contract), and defines a go-live gate. | Atomic duplicate detection, retention, lookup consistency and report/export contract are unconfirmed; no sandbox results exist. | Confirm the actual vendor contract and run the specified duplicate, timeout, restart and reconciliation sandbox tests before building/releasing. | High: incorrect assumptions could cause duplicate or lost payments. |
| A10 | The reconciliation node is connected conceptually to PayEx but has no asserted API/export mechanism. | The ADR calls for a daily safety net but lists PayEx report/export availability as unresolved. | Actual reconciliation source, cadence details and ownership are missing. | Confirm vendor export/API and define reconciliation procedure. | Medium to high: the intended control is clear, the integration mechanism is not. |
| A11 | Service Bus, `notification-worker`, and `audit-archive` are shown only as ops-scenario evidence, not as confirmed January application architecture. | The target-state document describes them as provisioned but unused; the ADR says not to put the PayEx path on Service Bus now. | Approved January decision for any event publisher/consumers and evidence that ops artifacts describe the deployment intended by this assignment are absent. | Confirm with the service owner; distinguish infrastructure provisioning from application publishing. | High for messaging scope; no Service Bus dependency is asserted on the payment path. |
| A12 | The dashed future outbox-to-Service-Bus relationship is conditional, not active. | The ADR only allows publishing from the outbox if other consumers appear later. | Whether those consumers are approved, event schemas, relay ownership and subscription contracts are unresolved. | Approve an eventing design and contracts before adding this link to a committed target architecture. | Medium: the conditional path is explicitly marked and must not be implemented as current target without approval. |
| A13 | `rowversion`/optimistic concurrency is shown separately as proposal-only. | The target-state diagram calls out rowversion, but its own note says this was a proposal rather than a specified design decision. | Owner decision, expected conflict behavior and schema contract are missing. | Confirm concurrency requirements and approve the data model/UX. | Medium: diagram does not represent it as a confirmed target dependency. |
| A14 | Alert delivery to an on-call role is drawn as a logical relationship; no monitoring product, channel or integration is implied. | The ADR lists required alert conditions and an on-call rotation/runbook but specifies no delivery system. | Alert platform, routing, escalation policy, and operational service ownership are absent. | Confirm monitoring and on-call design; test alert delivery. | Medium: operational responsibility is shown, concrete topology is not. |
| A15 | The phrase “dead letters” in the ADR alert list is not taken as evidence that the planned PayEx outbox uses Service Bus. | The ADR simultaneously excludes the PayEx path from Service Bus now; the target-state document's Service Bus details come from ops scenario evidence. | The intended source/meaning of the dead-letter alert is not resolved in the ADR. | Clarify the alert's data source with the ADR owner; update the target once decided. | Medium: prevents an unsupported Service Bus dependency from entering the target diagram. |
| A16 | Absence of a database, PayEx client and message publisher in the current app is based on the checked-in backend source and registration/dependency files, not on absence of records in `ops/`. | An as-built diagram must not convert plans or incident material into running components. | A separately deployed component outside this repository could exist, but no contract or runtime integration is evidenced by this code. | Inspect the actual deployed inventory only if the question concerns external deployment beyond this repository. | High for scope: diagrams describe this repository's current application, not an unverified surrounding environment. |
